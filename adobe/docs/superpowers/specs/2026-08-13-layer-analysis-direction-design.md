# 레이어 분리 판단을 연출 관점으로

작성일: 2026-08-13
대상: `auto_kairos_adobe` 레이어 분석(`analyze_scene_layers`) + 요소 스키마 + 패널 모달

## 문제

지금 분석은 **사물의 종류**로 판단한다 — 캐릭터인가, 캐릭터를 가리는 전경인가, 나레이션이 언급한 사물인가. 하지만 레이어를 나누는 목적은 분류가 아니라 **그 장면을 효과적으로 연출하는 것**이다.

더 구체적인 결함이 있다. 씬 이미지는 `image_prompt` 로 생성되고, 그 프롬프트는 나레이션을 잘 표현하려고 쓰였다 — **연출 의도가 거기 이미 적혀 있다.** 그런데 `backend/router.py` 의 analyze-layers 핸들러는 제목·요약·나레이션만 넘기고 `image_prompt` 는 넘기지 않는다.

실례(`projects/tesla` 씬 2):

```
image_prompt: 어두운 도로 위를 강하게 가속하며 출발하는 빨간 전기 스포츠카,
              낮은 차체와 선명한 전조등, 속도감 있는 빛의 궤적
```

의도는 "가속·속도감"이다. 그러면 차가 움직이고, 빛의 궤적이 따로 있어야 속도가 표현되고, 배경은 카메라로 흘려보내면 된다 → 차 / 빛의 궤적 / 배경. 현재 기준으로는 "차"(나레이션이 언급한 사물) 하나만 나온다.

## 설계

### 1. 판단 근거 확장

`analyze_scene_layers` 에 넘기는 맥락을 넓힌다.

| 입력 | 출처 | 목적 |
|---|---|---|
| `image_prompt` **(신규·핵심)** | 씬 필드 | 이 그림이 왜 이렇게 그려졌는지 = 연출 의도 원본 |
| `narration` (유지) | 씬 필드 | 무엇을 말하는 순간인지 |
| `title`·`visual_summary` (유지) | 씬 필드 | 씬의 요지 |
| 앞뒤 씬 **(신규)** | 앞/뒤 씬의 제목 + 나레이션 첫 60자 + `shot_relation` | 이어지는 샷이면 레이어 구성을 유지해야 연결이 자연스럽다 |
| 모션 어휘 **(신규)** | 상수 | 실행 가능한 동작만 상상하게 한다 |
| 프로젝트 브리핑 **(신규)** | `vault.read_context(proj_dir)` | 원고 전체 흐름의 요약 |

**원고 전문은 넣지 않는다.** 씬 하나를 분석할 때마다 127문단을 실으면 비용과 지연을 감당할 수 없다. 이미 존재하는 볼트 브리핑(600자 제한 요약)이 그 역할을 한다.

모션 어휘는 실제 구현된 것만 적는다: `slide_in` `fade_in` `pop` `drift` `bob` `shake` `zoom_emphasis` `exit_fade`, 카메라 `slow_zoom_in` `slow_zoom_out` `pan`, 그리고 레이어 앞뒤 배치로 얻는 패럴랙스.

### 2. 판단 기준 전환

프롬프트의 질문을 바꾼다.

1. 이 씬의 연출 의도는 무엇인가 (`image_prompt` 가 노린 것).
2. 그 의도를 살리려면 **무엇이 움직이거나 깊이를 가져야 하는가.**
3. 그 움직임을 만들려면 어떤 요소가 따로 떨어져 있어야 하는가.

기존 우선순위(캐릭터 → 가리는 전경 → 필요한 사물)는 버리지 않고 **연출 판단의 보조 기준**으로 남긴다. 특히 **인물은 항상 분리한다** — 움직일 것이 없어 보여도 까딱임(`bob`)으로 화면이 죽지 않게 하는 근거가 있다.

### 3. 최소성 — 상한과 같은 무게

`MAX_ELEMENTS = 4` 는 **상한이지 목표가 아니다.** 연출 중심으로 묻기 시작하면 없는 움직임을 지어내는 쪽으로 기울기 쉬우므로, 최소성을 프롬프트에 명시적으로 박는다.

- 목표는 **연출에 필요한 최소**다. 요소 1개(인물+배경 2레이어)가 가장 흔한 정답이고, 2~3개가 보통, 4개는 예외적이다.
- 반례를 프롬프트에 직접 넣는다: "인물 한 명이 말하는 씬은 인물 1장 + 배경 1장이면 충분하다. 더 쪼개도 연출이 나아지지 않으면 쪼개지 않는다."
- **요소마다 `intent` 를 요구하는 것 자체가 브레이크다.** 모션 어휘 중 무엇을 어떻게 쓸지 못 적으면 분리 근거가 없는 것이므로 그 요소는 배경에 남긴다.

비용도 같은 방향이다. 레이어당 과금 모델에서 불필요한 분리는 돈과 품질을 동시에 깎는다.

### 4. 스키마 확장

`backend/schemas/layer_elements.schema.json` 의 요소에 두 필드를 추가한다(둘 다 필수).

| 필드 | 내용 |
|---|---|
| `name_en` | 영어 이름. layerize 계열 모델의 프롬프트에 쓸 이름이며, 지금은 저장만 해도 무해하다 |
| `intent` | 이 레이어로 무엇을 할 것인가. 모션 어휘로 쓴다. 예: `"차량 본체 — slide_in 좌→우 후 drift로 가속 지속"` |

`reason`(왜 분리하는가)은 유지하되 연출 언어로 쓴다. `name`(한국어)은 패널 표시용으로 그대로 둔다.

`intent` 는 분리 시 요소 명세 사이드카(`layers/{sid}__elements.json`)에 함께 저장한다 — 이미 `name`·`location`·`kind` 를 저장하는 곳이다.

### 5. 모션 플랜으로의 전달

`plan_scene_motion` 은 지금 레이어 이름만 보고 처음부터 다시 판단한다. 사이드카에 `intent` 가 있으면 프롬프트에 함께 넣어, 분리 시점의 의도와 모션이 어긋나지 않게 한다.

**현재 모션 규칙은 그대로 둔다** — 캐릭터만 모션(`bob`), 사물 모션은 규칙 미정으로 금지. 따라서 사물 레이어의 `intent` 는 당분간 참고 정보로만 남고 키프레임이 되지는 않는다. 그 규칙을 바꾸는 것은 이 스펙의 범위 밖이다.

### 6. 패널

레이어 모달의 각 행에 `intent` 를 한 줄로 보여준다(지금 `reason` 을 보여주는 자리 아래). 사용자가 "왜 이게 나뉘는지"를 연출 언어로 판단할 수 있어야 한다.

상한 안내 문구를 `n/4 선택`에서 `n개 선택 (최대 4)`로 바꾼다 — 4개를 채워야 한다는 인상을 주지 않기 위해서다.

## 테스트

- `analyze_scene_layers` 에 넘긴 맥락 문자열에 `image_prompt` 본문, 앞뒤 씬 제목, 모션 어휘 8종, 브리핑이 실제로 들어가는지.
- 앞뒤 씬 조립: 첫 씬은 앞 씬 없음, 마지막 씬은 뒤 씬 없음으로 안전하게 처리되는지.
- 브리핑이 없는 프로젝트에서도 동작하는지.
- 스키마: `name_en`·`intent` 가 없는 응답은 검증에서 걸리는지.
- 사이드카 왕복: `intent` 가 저장되고 `load_element_specs` 로 다시 읽히는지.
- `plan_scene_motion` 프롬프트에 `intent` 가 포함되는지(사이드카가 없으면 없이도 동작).
- 패널 구조: 모달에 `intent` 표시와 바뀐 상한 문구가 있는지.

**분석 품질 자체는 자동 검증할 수 없다.** 테스트가 보장하는 것은 "맥락이 실제로 전달된다"까지다. 판단이 나아졌는지는 같은 씬을 이전 프롬프트와 새 프롬프트로 각각 분석해 사람이 비교해야 한다(분석 LLM 호출 2회).

## 범위 밖

- 레이어 분리 모델을 Seedream layerize로 바꾸는 것. 이번 분석 개선은 모델과 무관하게 유효하며, 오히려 분석 결과가 그대로 layerize 프롬프트가 되므로 더 잘 맞는다. 전환 여부는 배경 인페인팅 확인(실호출)을 거쳐 따로 정한다.
- 분리와 모션 플랜의 순서를 뒤집는 것.
- 사물 레이어 모션 규칙 신설.
- 원고 전문을 분석에 주입하는 것.
