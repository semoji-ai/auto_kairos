# 컨텍스트 주입 낭비 감사 (2026-08-04, LG편 실행 실측 기반)

> 배경: EP04~06 3편 생산에 5시간 리밋 70% 소모. codex에 리서치를 위임했음에도 과다 → Claude CLI 호출의 프롬프트 구성을 감사함.

## 결론 요약

가장 큰 낭비는 **script-director SKILL.md(69KB)를 챕터 병렬 호출마다 통째로 재주입**하는 것. 편당 약 9~10회 재주입되어 **편당 약 60만 자(≈27만 토큰)가 중복 투입**된다. 이것 하나가 전체 소모의 지배적 비중.

---

## 1. [치명] 챕터 병렬 처리 시 SKILL.md 전문 재주입

**위치**: `runner.py` `_run_chapter_*` (약 2890~3000행)

씬 분할 스텝(`step_2`)은 챕터 수만큼(LG편 기준 6~8개) 병렬 호출하는데, **각 호출 프롬프트에 `<agent_skill>` 태그로 69KB SKILL.md 전문을 매번 삽입**한다.

```
편당 script-director 호출 = 챕터 7회(step_2) + manuscript 1회 + consistency 1회 ≈ 9회
9 × 69KB = 621KB ≈ 27만 토큰 / 편 (중복분만)
```

**게다가 이 경로는 캐시를 안 탄다.** 코드에는 prompt caching 경로(`static_system` + `cache_control`, 3580~3600행)가 이미 구현돼 있으나, 챕터 병렬 경로는 그것을 쓰지 않고 CLI(`--print`)에 프롬프트를 평문 문자열로 넘긴다.

### 개선안 (효과 순)

**A. 모드별 SKILL 슬라이싱 (최우선, 80% 절감)**
챕터 분할 모드에 실제로 필요한 섹션은 전체의 약 1/5뿐이다.

| 섹션 | 크기 | chapters 모드 필요? |
|---|---|---|
| 다단계 실행 모드 | 12k | ❌ (이미 모드가 결정된 뒤) |
| 작업 흐름 | 14k | ❌ (manuscript 작성용) |
| 씬 스키마 | 7k | ✅ |
| 씬 분할 규칙 / headline / 모션 / 에셋 결정 | ~5k | ✅ |
| 나머지 규칙 | ~2k | ✅ |

→ SKILL.md를 `SKILL.md`(공통) + `mode-manuscript.md` + `mode-chapters.md`로 분할하고 모드에 맞는 것만 주입. 챕터 호출당 69KB → 약 14KB.

**B. 챕터 병렬 경로를 캐싱 SDK 경로로 전환** — ~~미적용~~ → **다른 방식으로 해결됨 (2026-09-08, `c34f4c3`)**

> ### ⚠️ 이 항목의 전제가 틀렸다
>
> 「CLI 라서 캐싱을 못 탄다」가 아니었다. **claude CLI 는 캐싱을 한다** —
> `usage` 에 `cache_creation_input_tokens` / `cache_read_input_tokens` 를 이미
> 주는데 `_parse_claude_cost` 가 버리고 있어서 안 보였을 뿐이다.
>
> 진짜 문제는 정적 블록이 **user 메시지(stdin)** 에 있다는 것이었다. 실측 —
> 같은 프롬프트 2회, chapters 슬라이스 57KB:
>
> ```
> --append-system-prompt-file   2회차  write      0  read 106,516
> stdin(user 메시지)             2회차  write 83,454  read  23,069
> ```
>
> **자리만 옮기면 된다.** SDK 전환도 API 키도 필요 없다.
>
> 그리고 SDK 전환은 캐싱을 켜는 일이 아니라 **과금 모델을 바꾸는 일**이다 —
> `CachingClaudeClient` 는 `anthropic` SDK 직접 호출이라 구독(claude CLI)에서
> API 과금으로 갈아타게 되고, `CLAUDE.md` 5절(「Anthropic API 직접 호출은 사용자
> 요청 시만」)과 충돌한다. 게다가 `api_key=""` 를 명시적으로 넘겨 자격증명 체인이
> 끊겨 있다 — 그 경로가 한 번도 안 쓰인 이유로 보인다.

캐시 write 레이스는 실재했다. 워밍을 붙여 해결했다.

```
워밍 없이 4개 동시   4개 전부  write 88,764  read 17,752   ← 캐시 공유 0
워밍 후   4개 동시   4개 전부  write 59,031  read 47,892
```

**7챕터 기준 약 20% 절감**(쓰기 1.25x·읽기 0.1x 환산, 워밍 호출 1회 포함).
「1/10 수준」이라는 위 추정은 **틀렸다** — 챕터마다 user 메시지가 달라 공유되는
prefix 가 시스템 프롬프트에서 끊긴다. 더 줄이려면 챕터별 컨텍스트 자체를 줄여야
하고 그건 별개 작업이다.

## 5. [신규·치명] wiki_compile — 비용 미기록 + resume 미적용 (2026-08-04 EP08에서 발견)

`step_1d_wiki_compile`은 **`cost_usd`를 기록하지 않는데 실제로는 claude CLI를 장시간 돌린다.**

**과소평가**다.

추가 문제: 이전 실행에서 이미 wiki를 만들었는데도 **resume이 스킵하지 않고 재컴파일**했다.

원인 추정 — `pipeline_state.json`에 중간 진행이 저장되지 않아(강제 종료 시 유실),

## 1-A 재검토 (2026-09-08, 캐싱이 붙은 뒤)

캐싱(1-B)이 붙었으니 물음이 바뀌었다. **더 자를 수 있나**가 아니라
**자르느라 잃은 게 있나**다.

### ① 잃은 것 — 하나 있었다 (고침, `2071731`)

「**chapters 모드 처리 규칙**」이라고 제목까지 붙은 규칙이 「모드 1.5(manuscript)」
섹션 안에 적혀 있었다. 슬라이싱이 정확히 거꾸로 배달했다.

```
chapters     그 규칙이 필요한 모드인데            ✗ 없음
manuscript   items/headline 손대는 게 금지인데    ✅ 있음
```

caption 마커를 **쓰는** 것은 manuscript 일, 그 항목을 씬 `items` 로 **옮기는** 것은
chapters 일이다. 옮기는 쪽을 「데이터 매핑 규칙」으로 이동했다.

**증상이 조용하다** — 규칙이 안 가면 caption 항목이 items 로 안 들어가고, 화면에만
띄우려던 용어·수치가 사라진다. 오류는 안 난다.

### ② 나머지 절삭은 깨끗하다

chapters 가 버리는 것은 **다른 모드의 지시와 다른 Step** 뿐이다(`drop_sections: []`).

```
### 모드 1 / 1.5 / 1.8 / 3      ← 다른 모드 소관
### Step 1 구조 설계 / Step 3 전체 검증  ← 다른 스텝 소관
```

manuscript 의 79% 절삭도 과하지 않다. SKILL 모드 1.5 가 스스로 이렇게 못박는다 —
「다른 모든 결정(layout, motion, mood, imageAsset, headline, items 등)은 이 모드의
책임이 **아닙니다**」. 절삭이 그 선을 그대로 따른다. **되돌릴 것이 없다.**

### ③ 그래도 슬라이싱은 유지한다 — 값어치는 떨어졌지만 여전히 이득

캐시는 쓰기 1.25x·읽기 0.1x 다. 자른 만큼이 캐시에서도 빠지므로 이득이 남는다.

| 스텝 | 호출 | 슬라이스 | 원본 | 절감 |
|---|---:|---:|---:|---:|
| chapters | 7 | 68,393 | 98,581 | 31% |
| manuscript | 1 | 14,018 | 66,609 | 79% |
| consistency | 1 | 31,570 | 66,609 | 53% |
| plan | 1 | 11,045 | 66,609 | 83% |
| **합계** | | **125,025** | **298,407** | **58%** |

다만 chapters 스텝에서 슬라이싱의 값어치는 **79% 떨어졌다**(절감 142,782 → 30,188).
캐싱 전에는 자른 만큼이 7번 다 청구됐는데, 이제 1번 쓰고 6번 싸게 읽기 때문이다.

호출이 1회뿐인 스텝(manuscript·plan·consistency)은 캐시 재사용이 없어 슬라이싱이
유일한 지렛대다 — 거기서는 값어치가 그대로다.

> 스텝 사이 캐시 공유는 계산에 넣지 않았다. 모드가 다르면 프리픽스가 갈리고,
> 스텝 간격이 캐시 TTL(5분)을 넘긴다.

**결론: 1-A 는 그대로 둔다.** 고칠 것은 잘못 놓인 규칙 하나뿐이었다.
