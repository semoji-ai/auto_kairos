# Auto Kairos 전체 파이프라인 Jev 적용 검토

검토일: 2026-09-19. 로컬 코드와 TypeSafe 공식 문서에 근거한 도입 설계 검토다. Jev 실호출·한국어 성능 측정·운영 코드 변경은 하지 않았다. 새 영상 프로젝트를 시작하지 않는다.

## 결론

Jev는 각 단계의 산출물을 작게 나누어 검사하는 판단 계층에 적합하다. 생성·검색·계산·시청각 검수는 기존 담당을 유지한다. 우선순위는 원본 가이드 충족 검사, 주장-근거 대조, 수정 전후 회귀 검사다. 문장 흐름 평가는 한국어 검증 뒤 확장한다.

## 확인한 실행 구조와 선행 과제

- `auto_agent/data/pipeline.json`: phase_0 → stage_1 → stage_2 → stage_3. 별도로 Stage 0 소재 탐색과 Stage 4 성과 분석이 `agent_runner.py` 및 관련 모듈에 존재한다. phase_0 사전 준비와 Stage 0 소재 탐색을 구분한다.
- v3 경로와 v4 bridge가 공존한다. bridge 산출물이 있으면 일부 legacy 단계가 스킵된다. 공통 산출물 경계에서 검사해야 경로에 따라 Jev가 누락되지 않는다.
- `brief_ratchet_v1`, `manuscript_ratchet`, `scene_ratchet`는 설정에 `blocking:false`가 있고 점수 무관 진행이라는 메모가 있다. 단, runner의 gate/FATAL 처리는 별도이므로 모든 실패가 무조건 통과한다는 뜻은 아니다. Jev의 판정과 최종 진행 결정을 연결하는 정책이 필요하다.
- 원고 리뷰 스킬 G4는 `advertiser_mandatory:true` 항목을 본문 필수로 검사한다. BTQ의 실제 brief는 문자열 must_cover 목록이고 원본 Excel의 세부 요구를 모두 보존하지 못했다. 평가 모델 교체에 앞서 원본 요구사항 목록을 확정해야 한다.
- `brief_review_module.py:review_brief`는 LLM 실패 시 휴리스틱 점수로 대체한다. 판단 출처를 기록하지만, 이를 독립 의미 검증과 동급으로 취급하면 안 된다.
- 별도 Adobe 텍스트 경로 `adobe/backend/pipeline.py:_run_judge`는 파싱 예외 시 pass를 반환한다. 이 경로의 오류를 PASS가 아닌 UNKNOWN으로 남기는 것이 개선 후보이며, Jev의 형식 보장만으로 서비스 장애까지 해결되는 것은 아니다.
- `narrative_consistency` 단계는 현재 설정에서 skip이다. 원고/씬 래칫에서 수행하는 흐름 검수와 별도 전역 일관성 단계가 실제로 실행되는지 구분해야 한다.

## 최초 적용: BTQ에서 놓친 것을 잡는 검수

입력은 요약 brief만이 아니라 원본 가이드에서 추출하고 사람이 검토한 요구사항을 포함한다. 제안 필드:

`requirement_id, source_file, source_sheet, source_cell, original_text, normalized_requirement, priority, allowed_delivery, verification_status`

- `priority`: mandatory / desired / reference. 원본이 불명확한 항목을 임의로 계약 의무로 승격하지 않는다.
- `allowed_delivery`: narration / screen / description. 화면 계획 존재와 실제 영상 반영을 별도 상태로 둔다.
- 모델에는 요구 1개와 관련 문단·근거만 전달한다. 전체 기록을 무조건 붙이지 않는다.
- 요구사항이 없거나 자료를 읽지 못했으면 N/A로 면제하지 않고 입력 미확정으로 기록한다.

BTQ 검사 질문 예시:

1. QCIM 문단은 칩에서 암호 알고리즘을 새 표준으로 바꿀 수 있다는 기능을 설명하는가?
2. QSSN을 금융/디지털자산 보안 네트워크로 설명하는가?
3. Bitcoin Quantum 구현을 별도 테스트넷으로 한정하는가?
4. PQC를 BTQ만의 독자 기술로 오인하게 하는가?
5. 정부가 BTQ를 선정했다고 암시하는가?
6. 정부 대응에서 기업 사례로 넘어가는 연결이 원고에 명시돼 있는가?

1~3은 가이드 충족, 4~5는 의미 오류, 6은 흐름 판단이다. 한 점수로 섞기 전에 별도 판정한다. Jev가 빠진 근거나 독자적 사실 확인을 만들어내도록 요구하지 않는다.

## 통합 구조 제안

`기존 작성/검색 → 코드 검사 → Jev 항목별 검사 → 코드의 판정 정책 → 필요 시 Codex 재검토·수정 → 재검사`

- 제안 신규 계층: `judge_client`, `judge_rubrics`, `judge_policy`. 현재 존재하는 구현을 뜻하지 않는다.
- 텍스트 생성용 AgentRunner provider에 그대로 넣지 않는다. Jev는 기존 agent의 자유문 생성 계약을 충족하지 못한다.
- 공통 산출물 경계: brief 확정 뒤, manuscript/claims 변경 뒤, scene_specs 변경 뒤, upload_info 작성 뒤. v4 bridge 경로도 포함한다.
- 판정 레코드: artifact hash, 요구사항/질문 버전, 모델 정확한 버전, source/span ID, 질문 유형, 원시 확률/score/confidence, 코드 정책 버전, 최종 상태, 사용량·지연.
- Jev는 자유문 이유나 인용을 생성하지 못한다. 기존 문장 ID/근거 ID 중 선택하도록 하거나 Codex가 이유를 작성하고 실제 원문 위치를 코드로 확인한다.
- 출력 상태: PASS / FAIL / UNKNOWN / ERROR. 장애·누락·낮은 확신을 PASS로 바꾸지 않는다.
- shadow에서는 결과 기록만 수행. 도입 후 필수 검수 UNKNOWN은 기존 리뷰어로 넘기며 조용히 통과시키지 않는다.
- 선택 확률, Noul 확률, 별도 confidence를 혼용하지 않는다. 질문별·모델버전별 검증으로 임계값을 정한다.

## 래칫 설계

1. 이전 점수와 원하는 최종 점수를 보여주지 않는 별도 평가를 둔다. 점수가 올라가야 한다는 압력과 실제 품질 개선을 분리한다.
2. 필수 누락·근거 모순 같은 하드 조건은 문체 점수로 상쇄하지 않는다.
3. A/B 후보를 익명화하고 순서를 바꿔 비교한다. 동률·둘 다 미달 선택지를 둔다.
4. 결과가 뒤집히면 자동 채택하지 않고 기존 리뷰어로 넘긴다.
5. 변경 없는 항목 캐시는 원고뿐 아니라 근거·루브릭·문맥의 해시가 동일할 때만 재사용한다. 문단 순서가 바뀌면 연결성은 다시 평가한다.
6. 품질이 실제로 악화되면 점수 하락을 허용한다. 보존하는 것은 마지막으로 검증된 산출물이며 점수 숫자 자체가 아니다.
7. 반복 수정은 제한 횟수/비용 내에서 수행한다. 사실 정정을 이전의 높은 점수 때문에 되돌리지 않는다.

## 검증 및 도입 순서

### 1. 고정 평가셋과 shadow

- BTQ 후보01~07 및 다른 영상 원고에서 100~200개 문항을 추출하는 작은 파일럿을 제안한다. 이 규모만으로 운영 안전성을 보장하지 않는다.
- 누락·과장·부분 충족·화면에만 존재·회사 주장 귀속·잘못된 수치·자연스러운 연결/연결 누락 사례를 포함한다.
- 사람이 라벨과 근거를 정하고 작성 모델과 분리한다. 기존91점은 정답으로 쓰지 않는다.
- 같은 영상의 유사 버전이 튜닝셋과 검증셋 양쪽에 섞이지 않도록 프로젝트 단위로 분리한다.
- 한국어 입력 유지. 영어 질문/한국어 질문을 비교하되 문체 검증을 위해 원고를 영어로 번역하지 않는다.
- 모델 버전 고정, 반복 평가 및 A/B 순서 편향 측정.
- 측정: 누락 탐지 재현율, 잘못된 통과율, 오경보율, UNKNOWN 비율, 사람과의 일치, calibration, p50/p95 지연, 호출비와 재검토비 합계.

### 2. 우선 운영 후보

요구사항 반영·근거 대조·윤문 회귀 검사부터 권고 모드로 적용한다. 회수 가능한 단순 분류에서 먼저 자동화를 시작한다. 한국어 자연스러움과 최종 원고 채택은 기존 리뷰를 유지한다.

### 3. 확대

검색 후보 필터와 업로드 텍스트 검수, 이후 소재 분류·성과 피드백으로 확장한다. 단계별 실측 효과가 없으면 유지하지 않는다. 렌더링/생성 시간이 지배적인 구간에서는 판단 비용 감소가 전체 제작 속도 증가로 직결되지 않는다.

## 비용과 적용 한계

현재 공식 가격은 입력100만 토큰당 $0.042, 출력 무료. 가정상 한 영상 검수 전체 입력이10만 토큰이면 $0.0042, 100만 토큰이면 $0.042다. 실제 청구량은 호출 기록으로 측정해야 한다. 검색·생성·Codex 재작성·TTS 비용은 별도다.

현재 `jev-1.13.0`은 텍스트만 입력받는다. 이미지·오디오·비디오 직접 QA를 대체하지 못한다. 영어 성능이 가장 좋고 CJK는 자체 검증이 필요하다고 공식 문서에 명시돼 있다. 현재 한도는 전체 요청64k, state+가장 긴 질문32k 토큰이다. 버전 고정과 관련 문맥만 선별하는 설계를 권한다.

정확한 계산, 날짜 비교, 글자수, 파일 존재, JSON 스키마, FFprobe 길이, 자막 시간, 렌더 완료는 코드로 처리한다. 연구 검색·수정 문장 작성·실제 시청각 검수·게시 승인은 해당 담당을 유지한다.

### 기존 검토의 확장

앞선 검토는 검수에 우선순위를 두었다. 이번 자료는 세 가지 추가 축을 보여준다.

1. 자료를 많이 읽고 분류하는 단계: Stage0 소재선별, Stage1 원문 관련성, 볼트 태깅, 경쟁 콘텐츠 분석. 생성 모델이 필요한 자료만 깊게 처리하게 하는 후보 필터다.
2. 후보를 조합하는 제작 단계: 알려진 Remotion 컴포넌트/구도/모션 중에서 선택. 이미지 생성 자체를 대체하지 않아도 연출 초안 결정의 일부를 담당할 수 있다.
3. 상태를 보고 다음 작업을 고르는 단계: 검수 결과에 따라 근거 재검색/문장 수정/연결 보강/기존 에이전트 검토를 선택한다. 원래 계획과 예산은 유지한다.

### 수정된 파일럿 제안

- A: 원본 가이드와 원고 검사 — 품질 문제를 직접 해결하는 기존P0 유지.
- B: 수집 자료 대량 관련성 분류 — 운영 효율을 측정하기 쉬운 조기 파일럿으로 격상. 원문 확보/요약/분류 비용을 별도로 계측.
- C: 제한된 Remotion 템플릿 선택 — 10~20개 정도의 이미 검증된 후보로 시험한다는 제안. 실제 후보 목록 존재 여부와 입력 계약은 구현 전 확인. 결과를 렌더한 뒤 시각 검증 유지.
- D: 반복 작업 분기 — 위 검사 신뢰도가 확보된 뒤 적용. 잘못된 분기의 비용이 크므로 즉시 전체 제어권을 맡기지 않음.

권장 역할: Codex가 새 문장·계획·코드를 만들고, Jev가 고정된 기준으로 후보와 다음 작업을 고르고, 코드가 실행·계산·예산·종료를 통제한다. 실제 시청각 내용이 필요하면 해당 인식/검수 도구를 앞뒤에 둔다.

항공권 캡처는 하단에 operation/index와 텍스트 작성의 역할을 나누는 표시가 있고, 논문 사례도 별도 모델의 요약 단계를 명시한다. 따라서 소개된 총체적 앱 기능을 모두 Jev 단독 능력으로 읽지 않는다. json-render 소개의 밀리초 표현과 화면의0.88초 등은 측정 지표가 같다고 가정하지 않는다.
